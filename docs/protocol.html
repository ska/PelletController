Stove serial protocol

How Pellet Controller talks to the stove board: line settings, message format, parameter map, polling, write verification and link handling. Code: serialproto.h / serialproto.cpp (SerialProto). Markdown version: PROTOCOL.md. Values in hexadecimal unless written otherwise; all sums modulo 256.

The stove board is a Micronova controller. The protocol is the same on every Micronova board, the parameter map is not: the map below was checked on this stove with a full memory dump (see Verified on the stove).

Line

SettingValue
Portsetting.ini in the working directory, [SERIAL] port, default /dev/ttyUSB0
Speed1200 baud
Frame8 data bits, no parity, 2 stop bits (8N2), no flow control
Byte time11 bits = about 9.2 ms
Echoyes: the line is shared, every byte sent comes back before the reply

setting.ini is optional:

[SERIAL]
port=/dev/ttyUSB0

The panel is the master: the stove board only answers requests. A reply is complete when the line stays idle for 100 ms (SERIAL_RX_IDLE_TIMEOUT).

Reply checks

ReplyAccepted whenOtherwise
Read4 bytes, the first 2 equal to the request, checksum matches counted (Err: length or echo, Chk: checksum), the parameter is read again once at the next tick
Write6 bytes, the first 4 equal to the request, byte 5 = checksum sent, byte 6 = value sent sent once more, then reported to the user (writeFailed)

A read that gets no byte at all (not even the echo) before the next request is a timeout: counted (Tmo) and read again once, like an invalid reply. A reply with the echo only (2 bytes) means the stove board did not answer (Err).

Top bar counters: Tx requests sent, Rx valid replies, Err replies with a wrong length or echo, Chk replies with a wrong checksum, Tmo requests without any reply. On this stove about 7 % of the requests got no reply during Ignition (2026-10-13), none with the stove Off.

Chrono programs

Verified on the stove

Full dump of RAM and EEPROM with tools/stovedump on 2026-10-13, stove Off, compared with the stove display:

  • Room temperature RAM 01 = 26 (19.0 °C), state RAM 21 = 0 (Off), smoke temperature RAM 5A = 21 °C, power EEPROM 7F = 2
  • Setpoint EEPROM 7D = 2D (45): the display shows 22.5 °C, so value / 2
  • Clock RAM 65-6B = 15 02 09 0C 0D 0A 1A: 21 s, Tuesday, 09:12, 13/10/26, the actual date and time
  • Weekend program 42-46 = 01 12 24 66 90: on, 03:00-06:00, 17:00-off, as on the stove display
  • Weekly program: the "slot off" times (90) are at 51/52, 5A/5B, 63/64, 6C/6D, a slot every 9 bytes as in the map above
  • EEPROM F8-FD = 02 09 13 13 10 26: the clock in BCD

RAM dump and three more reads 20 s apart with the stove in Pellet Loading (state RAM 21 = 2):

  • Auger RAM 0D = 37 (0 when Off)
  • Smoke fan speed RAM 37 = 199-201, about 2250 rpm (0 when Off)
  • Smoke temperature RAM 5A from 21 to 23 °C
  • Display text: scrolling, a different piece at each read

Ignition (state 3) and Working (state 4, power 2), three reads each:

  • Flame power RAM 34: 0 in Pellet Loading, 0-1 in Ignition, 4 in Working (shown as 32 %), steady
  • Smoke temperature RAM 5A: 68-72 °C in Ignition, 119 °C in Working
  • Smoke fan speed RAM 37: about 2450 rpm in Ignition, 1980 rpm in Working
  • RAM 19: 1 in Pellet Loading, 2 in Working at power 2 (90 Off)
  • During Ignition about 7 % of the requests got no reply at all

Polling

One request every 200 ms (SERIAL_MESSAGE_DELAY).

Main page: indexes 0-15, with the stove state every other request, then a 2 s pause (SERIAL_SESSION_DELAY). One round, about 8 s; the stove date and time is shown at its end:

01 21 0D 21 34 21 37 21 5A 21 65 21 66 21 67 21 68 21 69 21 6A 21 6B 21 7D 21 7F 21 4C 21

Chrono page: chrono on/off and all the chrono programs in order (indexes 15-62, 4C, then 42-74), then a 2 s pause; about 12 s per round.

An invalid reply is followed by one more read of the same parameter at the next tick, without moving the sequence on.

Writes

Queued and sent one at a time:

  1. The polling stops; the write is sent 150 ms later (SERIAL_WRITE_DELAY), after any read reply still arriving.
  2. The reply is awaited until the line is idle for 100 ms, at most 600 ms (SERIAL_WRITE_TIMEOUT).
  3. Not confirmed: sent once more (SERIAL_WRITE_ATTEMPTS = 2), then writeFailed and a message on the panel.
  4. Next write in the queue, or the polling restarts from the beginning after 600 ms.

A write with the serial port closed is reported at once.

Link handling

EventBehaviour
Port does not opentried again every 3 s (SERIAL_REOPEN_DELAY), logged once; panel shows "No serial port"
Port lost (USB adapter unplugged: resource, read or write error)port closed, polling stopped, setpoint and power to be read again; reopened every 3 s, polling restarts by itself
No valid reply for 10 s (SERIAL_NO_REPLY_TIMEOUT)panel shows "No reply"
Valid replylink OK, the next state read replaces the message

While the link is not OK the On/Off button is disabled.

Safety

Writes change the stove: setpoint, power, chrono and state are stored by the stove board (EEPROM for the settings). Never send writes to a real stove from a test: use the simulator tools/stovesim (README, "Stove simulator"), which the tests in tests/ use too.
